Zod JSON is a variant of Zod whose schemas are JSON Schema. A schema's enumerable properties are its JSON Schema keywords, the API has the shape of [Zod Mini](/packages/mini), and every keyword in JSON Schema 2020-12 is supported.

```sh
npm install zod @zod/json
```

```ts
import * as zj from "@zod/json";

const User = zj.object({
  name: zj.string().check(zj.minLength(1)),
  age: zj.optional(zj.integer().check(zj.minimum(0))),
  email: zj.optional(zj.string().check(zj.format("email"))),
});

type User = zj.infer<typeof User>;
// => { name: string; age?: number; email?: string }

User.parse({ name: "Ada", age: 36 }); // ✅
User.parse({ name: "", age: 36 }); // ❌ minLength
```

The schema is the document. Its own properties are JSON Schema keywords and nothing else.

```ts
User.type; // "object"
User.required; // ["name"]
User.properties.age; // { type: "integer", minimum: 0 }

JSON.stringify(User, null, 2);
```

```json
{
  "type": "object",
  "properties": {
    "name": { "type": "string", "minLength": 1 },
    "age": { "type": "integer", "minimum": 0 },
    "email": { "type": "string", "format": "email" }
  },
  "required": ["name"]
}
```

Three rules shape the package:

- **The schema is the document.** Parsing methods and Zod internals are non-enumerable, so `JSON.stringify()`, spread, and `Object.keys()` see a plain JSON Schema. Nested schemas are nested documents.
- **Zod Mini's shape.** Functions instead of methods, wrappers such as `zj.optional()`, and constraints through `.check()`. Names come from JSON Schema, not from Zod.
- **Every keyword.** Each keyword in JSON Schema 2020-12 is a builder, a check, or a metadata key, and each one is enforced the way the spec describes. Nothing is unrepresentable.

## Checks

Constraints go through `.check()`, as in Zod Mini. A check is named after the keyword it writes.

```ts
zj.string().check(zj.minLength(5), zj.maxLength(10));
// => { type: "string", minLength: 5, maxLength: 10 }
```

Every check is type-safe, so TypeScript rejects `zj.minItems()` on a string. The full list, by the type it applies to:

```ts
// strings
zj.minLength(n); // counts Unicode code points, as the spec requires
zj.maxLength(n);
zj.pattern(regex); // a RegExp or a string; a RegExp writes its source
zj.format(name); // every format the spec defines is asserted; any other name is an annotation

// numbers and integers
zj.minimum(n);
zj.maximum(n);
zj.exclusiveMinimum(n);
zj.exclusiveMaximum(n);
zj.multipleOf(n);

// arrays
zj.minItems(n);
zj.maxItems(n);
zj.uniqueItems();
zj.contains(schema);
zj.minContains(n);
zj.maxContains(n);
zj.unevaluatedItems(schema); // or false

// objects
zj.minProperties(n);
zj.maxProperties(n);
zj.propertyNames(schema);
zj.patternProperties({ [pattern]: schema });
zj.dependentRequired({ [key]: [...keys] });
zj.dependentSchemas({ [key]: schema });
zj.unevaluatedProperties(schema); // or false

// metadata, on any schema
zj.meta({ title, description, examples, deprecated, readOnly, writeOnly, $comment, $id, ...anything });
zj.describe(text);
```

## Strings

```ts
zj.string(); // { type: "string" }
zj.string().check(zj.minLength(1), zj.maxLength(255));
zj.string().check(zj.pattern(/^[a-z]+$/)); // { type: "string", pattern: "^[a-z]+$" }
```

The `format` keyword is asserted for every format the spec defines. The spec makes assertion optional; Zod JSON turns it on.

```ts
zj.string().check(zj.format("email")); // { type: "string", format: "email" }

// asserted formats
"date-time", "date", "time", "duration";
"email", "idn-email";
"hostname", "idn-hostname";
"ipv4", "ipv6";
"uri", "uri-reference", "iri", "iri-reference", "uri-template";
"uuid";
"json-pointer", "relative-json-pointer";
"regex";
```

Any other format name is written to the document and not checked.

```ts
zj.string().check(zj.format("credit-card")); // { type: "string", format: "credit-card" }
```

## Numbers

Both builders infer `number`. Infinity and `NaN` are rejected, since they are not JSON numbers.

```ts
zj.number(); // { type: "number" }
zj.integer(); // { type: "integer" }, accepts 1 and 1.0, rejects 1.5

zj.number().check(zj.minimum(0), zj.maximum(1));
zj.number().check(zj.exclusiveMinimum(0), zj.exclusiveMaximum(1));
zj.integer().check(zj.multipleOf(5));
```

## Booleans and null

```ts
zj.boolean(); // { type: "boolean" }
zj.null(); // { type: "null" }
```

## Literals and enums

Both accept any JSON value and compare structurally. The `type` keyword is written when every value has the same JSON type.

```ts
zj.const("admin"); // { type: "string", const: "admin" }
zj.const({ version: 1 }); // { type: "object", const: { version: 1 } }

zj.enum(["draft", "published"]); // { type: "string", enum: ["draft", "published"] }
zj.enum([0, 1, null]); // { enum: [0, 1, null] }
```

## Objects

A key is listed in `required` unless it is optional or has a default. The document describes the input.

```ts
const User = zj.object({
  id: zj.string().check(zj.format("uuid")),
  name: zj.string(),
  nickname: zj.optional(zj.string()),
  role: zj._default(zj.string(), "user"),
});
// => {
//   type: "object",
//   properties: {
//     id: { type: "string", format: "uuid" },
//     name: { type: "string" },
//     nickname: { type: "string" },
//     role: { type: "string", default: "user" },
//   },
//   required: ["id", "name"],
// }

type User = zj.infer<typeof User>;
// => { id: string; name: string; nickname?: string; role: string }
```

Unknown keys pass through, as in JSON Schema. The strict and catchall forms write `additionalProperties`.

```ts
zj.object({ name: zj.string() }); // unknown keys are allowed and kept
zj.strictObject({ name: zj.string() }); // additionalProperties: false
zj.catchall(zj.object({ name: zj.string() }), zj.number()); // additionalProperties: { type: "number" }
```

Records write `additionalProperties` and, for a constrained key, `propertyNames`.

```ts
zj.record(zj.string(), zj.number());
// => { type: "object", additionalProperties: { type: "number" } }

zj.record(zj.string().check(zj.pattern(/^x-/)), zj.string());
// => { type: "object", propertyNames: { type: "string", pattern: "^x-" }, additionalProperties: { type: "string" } }
```

The object checks constrain keys and key counts. None of them change the inferred type.

```ts
zj.object({ card: zj.optional(zj.string()), cvv: zj.optional(zj.string()) }).check(
  zj.minProperties(1),
  zj.maxProperties(10),
  zj.propertyNames(zj.string().check(zj.pattern(/^[a-z]+$/))),
  zj.patternProperties({ "^x-": zj.string() }),
  zj.dependentRequired({ card: ["cvv"] }), // cvv is required whenever card is present
  zj.dependentSchemas({ card: zj.object({ cvv: zj.string().check(zj.pattern(/^\d{3}$/)) }) }),
);
```

The object helpers return new documents.

```ts
zj.extend(User, { admin: zj.boolean() });
zj.pick(User, { id: true });
zj.omit(User, { role: true });
zj.partial(User); // every key optional; required is dropped
```

## Arrays and tuples

```ts
zj.array(zj.string()); // { type: "array", items: { type: "string" } }
zj.array(zj.string()).check(zj.minItems(1), zj.maxItems(10));
zj.array(zj.integer()).check(zj.uniqueItems()); // structural equality
zj.array(zj.integer()).check(zj.contains(zj.const(0)), zj.minContains(1), zj.maxContains(3));
```

Tuples write `prefixItems`. The `items` keyword is `false` unless a rest schema is given.

```ts
zj.tuple([zj.string(), zj.integer()]);
// => { type: "array", prefixItems: [{ type: "string" }, { type: "integer" }], items: false }

zj.tuple([zj.string()], zj.integer());
// => { type: "array", prefixItems: [{ type: "string" }], items: { type: "integer" } }
```

## Composition

The applicator keywords are functions.

```ts
zj.anyOf([zj.string(), zj.integer()]); // { anyOf: [...] }, string | number
zj.oneOf([zj.string(), zj.integer()]); // { oneOf: [...] }, exactly one must match
zj.allOf([User, Timestamps]); // { allOf: [...] }, User & Timestamps
zj.not(zj.const(null)); // { not: { const: null } }, unknown
```

Nullability writes a `type` array when the inner schema is a bare type, and an `anyOf` otherwise.

```ts
zj.nullable(zj.string()); // { type: ["string", "null"] }
zj.nullable(zj.string().check(zj.minLength(1))); // { anyOf: [{ type: "string", minLength: 1 }, { type: "null" }] }
```

Conditionals take the `if` schema and its `then` and `else` branches. The output type is the union of the two branches, so a conditional usually sits inside an `allOf` next to the object it constrains.

```ts
const Shape = zj.allOf([
  zj.object({
    kind: zj.enum(["circle", "rect"]),
    radius: zj.optional(zj.number()),
    width: zj.optional(zj.number()),
    height: zj.optional(zj.number()),
  }),
  zj.if(zj.object({ kind: zj.const("circle") }), {
    then: zj.object({ radius: zj.number() }),
    else: zj.object({ width: zj.number(), height: zj.number() }),
  }),
]);
```

The unevaluated keywords apply to whatever the applicators around them did not cover. They are checks on the composite, and they see every key or item that `properties`, `patternProperties`, `additionalProperties`, `prefixItems`, `items`, `contains`, `allOf`, `anyOf`, `oneOf`, `if`, `then`, `else`, `dependentSchemas`, and `$ref` evaluated.

```ts
zj.allOf([User, Timestamps]).check(zj.unevaluatedProperties(false));
// => { allOf: [...], unevaluatedProperties: false }
// a key that neither User nor Timestamps declares is rejected

zj.allOf([zj.tuple([zj.string()]), zj.array(zj.unknown()).check(zj.contains(zj.integer()))]).check(
  zj.unevaluatedItems(zj.boolean()),
);
```

The boolean schemas `true` and `false` are the empty schema and its negation.

```ts
zj.any(); // {}
zj.unknown(); // {}
zj.never(); // { not: {} }
```

## References

A recursive schema is a getter, and `zj.toJSONSchema()` writes the cycle as a `$ref`.

```ts
const Category = zj.object({
  name: zj.string(),
  get children() {
    return zj.array(Category);
  },
});

zj.toJSONSchema(Category);
// => {
//   type: "object",
//   properties: {
//     name: { type: "string" },
//     children: { type: "array", items: { $ref: "#" } },
//   },
//   required: ["name", "children"],
// }
```

A reference is also a schema of its own. It resolves at parse time against the document it sits in: `#` is the resource root, `#/$defs/name` is a definition, and `#name` is an `$anchor`. Its inferred type is `unknown`.

```ts
const Tree = zj
  .object({
    value: zj.number(),
    children: zj.array(zj.ref("#/$defs/node")),
  })
  .check(
    zj.meta({
      $defs: {
        node: zj.object({ value: zj.number(), children: zj.array(zj.ref("#/$defs/node")) }),
      },
    }),
  );

const Address = zj.object({ city: zj.string() }).check(zj.meta({ $anchor: "address" }));
zj.ref("#address");
```

An `$id` starts a new resource, so references inside it resolve against it. A `$ref` to another `$id` is looked up in the schemas passed to `zj.fromJSONSchema()` or registered with `zj.registry`.

```ts
const Address = zj.object({ city: zj.string() }).check(zj.meta({ $id: "https://example.com/address" }));

zj.object({ home: zj.ref("https://example.com/address") });
```

Dynamic references resolve against the outermost `$dynamicAnchor` of the same name in the dynamic scope, which is how a generic container is specialized by the schema that includes it.

```ts
const List = zj
  .object({ items: zj.array(zj.dynamicRef("#item")) })
  .check(zj.meta({ $id: "https://example.com/list", $defs: { item: zj.any().check(zj.meta({ $dynamicAnchor: "item" })) } }));

const NumberList = zj
  .allOf([zj.ref("https://example.com/list")])
  .check(zj.meta({ $defs: { item: zj.number().check(zj.meta({ $dynamicAnchor: "item" })) } }));
```

## Metadata

Annotation keywords are written by `zj.meta()` and `zj.describe()`. In Zod Mini these register the schema in `z.globalRegistry`; in Zod JSON they write onto the document.

```ts
zj.string().check(
  zj.meta({ title: "Display name", examples: ["ada"], deprecated: true }),
  zj.describe("Shown on the profile page"),
);
// => {
//   type: "string",
//   title: "Display name",
//   examples: ["ada"],
//   deprecated: true,
//   description: "Shown on the profile page",
// }
```

The content keywords are annotations, as the spec's default vocabulary defines them.

```ts
zj.string().check(zj.meta({ contentMediaType: "application/json", contentEncoding: "base64", contentSchema: User }));
```

The core keywords `$schema`, `$vocabulary`, and `$comment` are annotations on the root.

```ts
zj.object({}).check(zj.meta({ $schema: "https://json-schema.org/draft/2020-12/schema", $comment: "generated" }));
```

Keys that Zod JSON does not know are written verbatim, which is how OpenAPI extensions travel.

```ts
zj.string().check(zj.meta({ "x-internal": true, example: "ada" }));
// => { type: "string", "x-internal": true, example: "ada" }
```

## Errors

The `error` parameter customizes the message, as in Zod Mini. It is not a keyword and does not appear in the document.

```ts
zj.string({ error: "Expected a string" }).check(zj.minLength(8, { error: "At least 8 characters" }));
```

Issues are the `$ZodIssue` objects every Zod package produces, so [error formatting](/error-formatting) and [locales](/error-customization#internationalization) work unchanged. Like Zod Mini, Zod JSON loads no locale by default.

```ts
import * as zj from "@zod/json";

zj.config(zj.locales.en());
```

## `zj.toJSONSchema()`

For a schema without cycles, `JSON.stringify()` is the conversion. The function exists for cycles, shared subschemas, and older drafts.

```ts
zj.toJSONSchema(User); // the same document JSON.stringify() produces
zj.toJSONSchema(Category); // the cycle becomes { $ref: "#" }
zj.toJSONSchema(User, { reused: "ref" }); // a schema used twice becomes a $def
zj.toJSONSchema(User, { cycles: "throw" });
zj.toJSONSchema(User, { target: "draft-07" }); // exclusiveMinimum as a boolean, prefixItems as an items array, $defs as definitions
zj.toJSONSchema(User, { target: "draft-04" });
zj.toJSONSchema(User, { target: "openapi-3.0" }); // nullable instead of type: "null", no const or prefixItems
```

There is no `unrepresentable`, `io`, `override`, or `metadata` option. Nothing is unrepresentable, the document already describes the input, and metadata is on the schema.

An `$id` names the schema in `$defs` and in the `$ref` that points at it.

```ts
const Address = zj.object({ city: zj.string() }).check(zj.meta({ $id: "Address" }));

zj.toJSONSchema(zj.object({ home: Address, work: Address }), { reused: "ref" });
// => {
//   type: "object",
//   properties: { home: { $ref: "#/$defs/Address" }, work: { $ref: "#/$defs/Address" } },
//   required: ["home", "work"],
//   $defs: { Address: { $id: "Address", type: "object", properties: { city: { type: "string" } }, required: ["city"] } },
// }
```

The Standard Schema interface exposes the document too.

```ts
User["~standard"].jsonSchema.input; // the schema itself
```

## `zj.fromJSONSchema()`

A JSON Schema document becomes a Zod JSON schema. Pass it `as const` and the TypeScript type is inferred from the document.

```ts
const Point = zj.fromJSONSchema({
  type: "object",
  properties: { x: { type: "number" }, y: { type: "number" } },
  required: ["x", "y"],
} as const);

type Point = zj.infer<typeof Point>; // { x: number; y: number }
Point.parse({ x: 1, y: 2 });
```

Without `as const` the schema still parses, and the inferred type is `unknown`.

The reader accepts any 2020-12 document, and draft-04, draft-07, and OpenAPI 3.0 documents by their `$schema`. It resolves `$ref`, `$anchor`, `$dynamicRef`, and `$dynamicAnchor` within the document, and external `$ref` targets from the `schemas` option. A `type` array becomes an `anyOf` of its members, each carrying the keywords that apply to it. Unknown keywords are kept. The result round-trips: `zj.toJSONSchema(zj.fromJSONSchema(doc))` deep-equals `doc`.

```ts
const Order = zj.fromJSONSchema(orderDoc, { schemas: [addressDoc, customerDoc] });
```

## Interop with `zod`

A Zod JSON schema is a core schema, so it nests inside `zod` and `zod/mini` containers. Refinements and transforms belong to the outer schema, since JSON Schema cannot express them.

```ts
import * as zj from "@zod/json";
import * as z from "zod";

const Signup = z
  .object({
    user: User, // a Zod JSON schema
    password: z.string().min(8),
  })
  .refine((v) => v.password !== v.user.name, { error: "Password cannot be your name" });
```

The two packages differ where JSON Schema and Zod disagree on a default, and where a keyword has a different name.

| | `zod/mini` | `@zod/json` |
| --- | --- | --- |
| Unknown object keys | stripped | passed through; `zj.strictObject()` rejects them |
| Defaulted key in the document | required | not required; the document describes the input |
| String length | UTF-16 code units | Unicode code points |
| Default locale | `en` | none |
| Dates, bigints, maps, sets, `undefined` | schemas | not JSON, not available |
| Coercion, transforms, refinements | built in | in the enclosing `zod` schema |
| Metadata | `z.globalRegistry` | keywords on the schema |
| String formats | `z.email()`, `z.iso.datetime()`, `z.url()`, ... | `zj.format("email")`, `zj.format("date-time")`, `zj.format("uri")`, ... |
| Literals | `z.literal()` | `zj.const()` |
| Unions | `z.union()`, `z.xor()`, `z.intersection()` | `zj.anyOf()`, `zj.oneOf()`, `zj.allOf()` |
| Integers | `z.int()` | `zj.integer()` |
| Regex | `z.regex()` | `zj.pattern()` |
| Number bounds | `z.gte()`, `z.gt()`, `z.lte()`, `z.lt()` | `zj.minimum()`, `zj.exclusiveMinimum()`, `zj.maximum()`, `zj.exclusiveMaximum()` |

## Keyword reference

Every keyword in JSON Schema 2020-12 and what writes it.

| Keyword | Written by | Runtime |
| --- | --- | --- |
| `type` | every builder, `zj.nullable()` | validated |
| `properties`, `required` | `zj.object()`, `zj.optional()`, `zj._default()` | validated |
| `additionalProperties` | `zj.strictObject()`, `zj.catchall()`, `zj.record()` | validated |
| `patternProperties`, `propertyNames`, `minProperties`, `maxProperties`, `dependentRequired`, `dependentSchemas`, `unevaluatedProperties` | the check of the same name | validated |
| `items`, `prefixItems` | `zj.array()`, `zj.tuple()` | validated |
| `minItems`, `maxItems`, `uniqueItems`, `contains`, `minContains`, `maxContains`, `unevaluatedItems` | the check of the same name | validated |
| `minLength`, `maxLength`, `pattern` | the check of the same name | validated |
| `format` | `zj.format()` | asserted for the nineteen spec formats, otherwise an annotation |
| `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `multipleOf` | the check of the same name | validated |
| `const`, `enum` | `zj.const()`, `zj.enum()` | validated, structural equality |
| `anyOf`, `oneOf`, `allOf`, `not` | `zj.anyOf()`, `zj.oneOf()`, `zj.allOf()`, `zj.not()`, `zj.nullable()` | validated |
| `if`, `then`, `else` | `zj.if()` | validated |
| `$ref`, `$dynamicRef` | `zj.ref()`, `zj.dynamicRef()`, getters | resolved at parse time |
| `$id`, `$anchor`, `$dynamicAnchor`, `$defs` | `zj.meta()`, `zj.toJSONSchema()` | reference targets |
| `default` | `zj._default()` | applied when the value is `undefined` |
| `title`, `description`, `examples`, `deprecated`, `readOnly`, `writeOnly` | `zj.meta()`, `zj.describe()` | annotation |
| `contentEncoding`, `contentMediaType`, `contentSchema` | `zj.meta()` | annotation |
| `$schema`, `$vocabulary`, `$comment` | `zj.meta()`, `zj.toJSONSchema()` | annotation |
| anything else | `zj.meta()` | written verbatim |

## Zod Core additions

This section is the workpiece and is deleted before the page ships. Zod JSON is built from `zod/v4/core` primitives, and these are the ones the core does not have yet. Each row is one core change; the Zod JSON layer on top of it is the naming and the enumerable-keyword instance.

| Keyword | Core today | Core addition |
| --- | --- | --- |
| `not` | nothing | `$ZodNot`, a schema that succeeds when its inner schema fails |
| `if`, `then`, `else` | nothing | `$ZodConditional`, evaluates `then` or `else` by the result of `if` |
| `$ref`, `$dynamicRef` | `$ZodLazy` with a getter | `$ZodRef`, resolved at parse time; the parse context gains a resource stack (`$id` boundaries) and a dynamic scope (`$dynamicAnchor` targets) |
| `unevaluatedProperties`, `unevaluatedItems` | nothing | an evaluated-keys and evaluated-items annotation on the parse payload, written by `$ZodObject`, `$ZodArray`, `$ZodTuple`, `$ZodUnion`, `$ZodXor`, `$ZodIntersection`, `$ZodConditional`, `$ZodRef`, and the `dependentSchemas` check; two checks that read it |
| `const`, `enum` with objects or arrays | `$ZodLiteral` and `$ZodEnum` compare primitives with `===` | structural equality for object and array members |
| `uniqueItems`, `contains`, `minContains`, `maxContains` | enforced inside `z.fromJSONSchema()` only ([#6535](https://github.com/colinhacks/zod/pull/6535)) | four core checks |
| `minProperties`, `maxProperties` | on the `min-max-properties` branch ([#6493](https://github.com/colinhacks/zod/pull/6493), closed) | land the two checks |
| `propertyNames` | enforced inside `z.fromJSONSchema()` only ([#6411](https://github.com/colinhacks/zod/pull/6411)) | one core check |
| `patternProperties`, `dependentRequired`, `dependentSchemas` | nothing | three core checks |
| `minLength`, `maxLength` | `$ZodCheckMinLength` and `$ZodCheckMaxLength` count UTF-16 code units | a code-point mode, since the spec counts characters |
| `format` | `email`, `hostname`, `ipv4`, `ipv6`, `uuid`, `date-time`, `date`, `duration`, `uri` (as `url`) | `idn-email`, `idn-hostname`, `uri-reference`, `iri`, `iri-reference`, `uri-template`, `json-pointer`, `relative-json-pointer`, `regex`; and `time` with the mandatory RFC 3339 offset, which `$ZodISOTime` does not require |
| `allOf` | `$ZodIntersection` is binary | an n-ary form, or nesting in the Zod JSON layer |
| `type` arrays | nothing | a multi-type schema whose keywords apply by the instance's type, if byte-identical round-trips matter (see open questions) |
| `$id`, `$anchor`, `$dynamicAnchor`, `$defs` | `z.globalRegistry` metadata | the resolver that `$ZodRef` calls; lives in Zod JSON |
| `~standard.jsonSchema` | classic builds it from `toJSONSchema()`; mini has none | the Zod JSON instance returns itself |

## Open questions

This section is the workpiece and is deleted before the page ships. Each item names the choice the page makes and the alternative.

1. **Unknown object keys.** The page passes them through, which is what JSON Schema validation does. Zod strips them, and a stripped output still conforms to the document.
2. **What `required` describes.** The page lists a defaulted key as not required, so the document describes the input. Zod's `z.toJSONSchema()` describes the output by default and lists it as required.
3. **Format sugar.** The page has one spelling, `zj.string().check(zj.format("email"))`. Builders such as `zj.email()` would shorten the common case at the cost of nineteen more exports.
4. **Content assertions.** The page treats `contentEncoding`, `contentMediaType`, and `contentSchema` as annotations, which is the spec's default. The spec also allows asserting them: decode the encoding, then validate the decoded content against `contentSchema` when the media type is JSON.
5. **Type arrays.** A `type: ["string", "number"]` with `minLength` and `minimum` beside it reads back as an `anyOf` with the keywords distributed. That round-trips semantically, not byte for byte. A multi-type core schema would make it exact.
6. **Nullable shape.** A `type` array for a bare inner type and `anyOf` otherwise, matching Zod's emitter. Always writing `anyOf` is simpler and one line longer.
7. **Discriminated unions.** No keyword exists. `zj.anyOf()` and `zj.oneOf()` cover the semantics and lose the discriminator fast path and the targeted error. A `zj.discriminatedUnion()` that writes `anyOf` plus OpenAPI's `discriminator` is the middle ground.
8. **Unknown keywords through `zj.meta()`.** Written verbatim, which OpenAPI's `x-` extensions need, and a misspelled keyword is accepted silently.
9. **Package shape.** A standalone `@zod/json` with a peer dependency on `zod`, like `@zod/mini`. Not decided: whether it is also a `zod/json` subpath, and whether the source lives in `packages/json` or `packages/zod/src/v4/json`.
10. **Out of scope for the first release.** Multi-document output from a registry, `zj.compile()` support for the new schema types, and moving the classic `z.toJSONSchema()` emitter out of `zod`.
