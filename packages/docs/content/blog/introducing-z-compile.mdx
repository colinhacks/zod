Zod 4.5 can compile a schema into a specialized validator ahead of time, and on arrays, unions, and nested or wide objects the compiled schema parses 4–14x faster with exactly the same output and exactly the same errors.

```ts
import * as z from "zod";

const Player = z.object({
  username: z.string(),
  bio: z.string(),
  xp: z.number(),
  level: z.number(),
  rank: z.number(),
  admin: z.boolean(),
  stats: z.object({ title: z.string(), score: z.number(), active: z.boolean() }),
});

const CompiledPlayer = z.compile(Player); // parses ~4.5x faster
```

`CompiledPlayer` is a regular Zod schema. Use it exactly like `Player`:

- It has every method the original has — `.parse()`, `.safeParse()`, `.extend()`, `.optional()`, Standard Schema — and it composes into other schemas.
- Its inferred input and output types are identical.
- On failure it returns identical issues.

Zod's entire test suite runs twice, once against uncompiled schemas and once with compilation enabled globally, asserting per fixture that the compiled path produced every value rather than silently falling back.

Under the hood, `z.compile()` walks the entire schema once and generates a specialized fast-path validator with the `Function` constructor. For the large majority of inputs, that function validates the data with the fastest logic JavaScript can express: straight-line `typeof` checks and property reads, with no interpreter in between. When the fast path can't handle an input, Zod falls back to the standard parser.

## Compile everything with one import

You don't have to call `z.compile()` per schema. Import `zod/compile` once, before anything that defines schemas, and every schema constructed after that is compiled on its first parse:

```ts
import "zod/compile"; // must come before modules that define schemas
import * as z from "zod";

const schema = z.object({ name: z.string() });
schema.parse({ name: "ok" }); // compiled on first parse
```

Compilation is lazy, so the intermediate schemas inside a builder chain like `z.string().min(1).max(10).optional()` cost nothing. Only the schemas you actually parse with get compiled.

This import is for applications, not libraries. A library that imports `zod/compile` opts in every schema in the process on behalf of its users, which is not its decision to make.

What compilation removes is per-node dispatch and allocation, not the checks themselves, so the win scales with how many nodes a parse walks. Containers benefit most.

```ts
// 20-key object — 8.9x
z.object({ k0: z.string(), k1: z.string(), /* … */ k19: z.string() });
```

```ts
// union of 3 objects — 8.4x
z.union([z.object({ a: z.string() }), z.object({ b: z.number() }), z.object({ c: z.boolean() })]);
```

```ts
// tuple of 3 — 4.8x
z.tuple([z.string(), z.number(), z.boolean()]);
```

A bare `z.string()` has nothing to remove: the whole schema is one `typeof`. Everything built out of such schemas still benefits, because leaves are inlined into the parent's generated code.

These numbers come from the repo's 55-schema `compile-matrix` benchmark, run with all 55 schemas sharing one process, where the median is 2.4x. Measured one schema per process, the median is 1.6x. Both are real: every schema shares zod's internal dispatch sites, and running many of them together makes those call sites megamorphic, which taxes the interpreter more than it taxes a generated function. The shared number is the default because an application holds many schemas at once, and that is the speedup its users see.

Four corrections to the harness were needed before these numbers meant anything, and they are written up in the repo:

- Results must escape. V8 deletes a parse whose result is discarded; `z.string()` measured 625M ops/sec before this was fixed.
- Inputs must arrive through an array load, not a constant, or the call becomes loop-invariant.
- The number of schemas sharing the process is the single largest lever on the result.
- Compiled and uncompiled runs must be interleaved, because absolute throughput drifts by tens of percent between runs.

## What the compiler generates

Zod schemas are trees, and parsing one is a walk over that tree: each node receives a payload, checks its value, runs its checks, and hands the payload to its children. That walk is what makes Zod composable, and it is also what makes it slow. Every node pays for dispatch, a payload allocation, and path tracking, whether the node is a twenty-key object or a bare `typeof`.

Compilation flattens the walk into straight-line code. This is the function Zod generates for the `Player` schema above:

```js
if (typeof input !== "object" || input === null || Array.isArray(input)) return INVALID;
const v0 = input["username"];
if (typeof v0 !== "string") return INVALID;
const v1 = input["bio"];
if (typeof v1 !== "string") return INVALID;
const v2 = input["xp"];
if (typeof v2 !== "number" || !Number.isFinite(v2)) return INVALID;
const v3 = input["level"];
if (typeof v3 !== "number" || !Number.isFinite(v3)) return INVALID;
const v4 = input["rank"];
if (typeof v4 !== "number" || !Number.isFinite(v4)) return INVALID;
const v5 = input["admin"];
if (typeof v5 !== "boolean") return INVALID;
const v6 = input["stats"];
if (typeof v6 !== "object" || v6 === null || Array.isArray(v6)) return INVALID;
const v7 = v6["title"];
if (typeof v7 !== "string") return INVALID;
const v8 = v6["score"];
if (typeof v8 !== "number" || !Number.isFinite(v8)) return INVALID;
const v9 = v6["active"];
if (typeof v9 !== "boolean") return INVALID;
const v10 = { "title": v7, "score": v8, "active": v9 };
const v11 = { "username": v0, "bio": v1, "xp": v2, "level": v3, "rank": v4, "admin": v5, "stats": v10 };
return v11;
```

No payloads, no dispatch, no path arrays. Leaf schemas are inlined into their parent, so a `z.string()` inside an object costs one `typeof`, and the nested `stats` object costs nothing beyond its own three checks.

## Why this was hard

The obvious way to build a compiler is to generate everything: one code path that validates, and one that produces the errors when validation fails. For Zod that would mean a second implementation of every schema type and every check, agreeing with the first on every edge case: dozens of schema types, dozens of checks, 60 locales, and years of error shapes that people snapshot in their test suites. A second implementation of all that was never going to stay in sync.

So Zod's compiler doesn't produce errors at all. Look at the generated code again: every failure is `return INVALID`. The compiled function is a happy-path validator, and when it returns `INVALID`, the wrapper hands the input to the standard parser, which produces the `ZodError` the same way it always has.

```ts
const player = { username: "billie", bio: "hi", xp: 100, level: 3, rank: 12, admin: false, stats: { title: "pro", score: 9000, active: true } };

const result = CompiledPlayer.safeParse({ ...player, xp: "100", stats: { ...player.stats, active: "yes" } });
result.error.issues;
// [
//   {
//     expected: "number",
//     code: "invalid_type",
//     path: ["xp"],
//     message: "Invalid input: expected number, received string"
//   },
//   {
//     expected: "boolean",
//     code: "invalid_type",
//     path: ["stats", "active"],
//     message: "Invalid input: expected boolean, received string"
//   }
// ]
```

That is the error the uncompiled `Player` produces, because the fallback ran the uncompiled `Player` to build it. There is no second error path to drift out of sync, and every fix to the standard parser's error reporting applies to compiled schemas automatically.

Two consequences follow:

- An invalid input runs the fast path and then the standard parser, so compilation itself doesn't speed up failures. Failures got their own speedup in 4.5: `ZodError` construction is now lazy and skips the eager stack capture on the `safeParse()` path, so a failing `safeParse()` is 3–4x faster than in 4.4 ([#6316](https://github.com/colinhacks/zod/pull/6316), [#6450](https://github.com/colinhacks/zod/pull/6450)).
- Refinements and transforms run exactly once on valid input, and at most twice on invalid input: once in the fast path, once in the fallback.

## What falls back

A few constructs stay on the existing runtime implementation instead of compiling. `z.compile()` throws on them; global mode quietly keeps using the standard parser. Nothing changes in their behavior; they just don't get faster.

- async refinements, transforms, and checks, and `safeParseAsync()`
- `z.xor()`
- recursive schemas
- `z.coerce.*`, checks with a custom `when`, and `.catch()` given a callback
- encoding (`z.encode()` and the codec `"backward"` direction)
- CSP environments, where `new Function` is unavailable: global mode stands down under `z.config({ jitless: true })`, and `z.compile()` throws `ZodCompileUnsupportedError`

Inside an object, array, tuple, record, or intersection, an unsupported child runs on the standard parser while the surrounding structure stays compiled.

Methods that derive a new schema return uncompiled schemas, so compile the final schema, not an intermediate:

```ts
// ❌ the .refine() result is not compiled
const schema = z.compile(z.string()).refine((val) => val.length > 1);

// ✅ compile last
const schema2 = z.compile(z.string().refine((val) => val.length > 1));
```

## Cost

A compiler is a lot of code, so the question is what it costs a bundle that never uses it. The compiler itself tree-shakes cleanly: unless you call `z.compile()` or import `zod/compile`, none of it ends up in your bundle.

What every bundle does carry is the hook that global mode needs in the schema constructor. It measured at +21 to +25 bytes gzipped on the smallest `zod/mini` fixtures and below the noise floor on construction speed, and the bundle-size test in CI now holds those fixtures to a ceiling.

## Try it

```sh
npm install zod@^4.5.0
```

Then `z.compile()` the schema on your hottest path, or `import "zod/compile"` at the top of your entry point, and run your test suite. If anything comes out different from the uncompiled schema, that's a bug — [file it](https://github.com/colinhacks/zod/issues). The [compile docs](/compile) have the full reference.
