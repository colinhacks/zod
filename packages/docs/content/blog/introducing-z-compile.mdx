Zod 4.5 can compile a schema into a specialized validator ahead of time, and the result parses about 2.4x faster with exactly the same output and exactly the same errors.

```ts
import * as z from "zod";

const Player = z.object({
  username: z.string().min(2),
  xp: z.number().int(),
  tags: z.array(z.string()),
});

const CompiledPlayer = z.compile(Player);

CompiledPlayer.parse({ username: "billie", xp: 100, tags: ["a"] });
// { username: 'billie', xp: 100, tags: [ 'a' ] }
```

The thing that comes back from `z.compile()` is a regular Zod schema. `.parse()`, `.safeParse()`, type inference, Standard Schema, and composition all work exactly as before, and the original schema is untouched.

## What the compiler generates

Zod schemas are trees, and parsing one is a walk over that tree: each node receives a payload, checks its value, runs its checks, and hands the payload to its children. That walk is what makes Zod composable, and it is also what makes it slow. Every node pays for dispatch, a payload allocation, and path tracking, whether the node is a twenty-key object or a bare `typeof`.

Compilation flattens the walk into straight-line code. This is the function Zod generates for the `Player` schema above:

```js
if (typeof input !== "object" || input === null || Array.isArray(input)) return INVALID;
const v0 = input["username"];
if (typeof v0 !== "string") return INVALID;
const v1 = typeof v0 === "string" && v0.length >= 2 && v0.length < 4 ? c0(v0) : v0.length;
if (v1 < 2) return INVALID;
const v2 = input["xp"];
if (typeof v2 !== "number" || !Number.isFinite(v2)) return INVALID;
if (!Number.isSafeInteger(v2)) return INVALID;
const v3 = input["tags"];
if (!Array.isArray(v3)) return INVALID;
const v4 = new Array(v3.length);
for (let v5 = 0; v5 < v3.length; v5++) {
  const v6 = v3[v5];
  if (typeof v6 !== "string") return INVALID;
  v4[v5] = v6;
}
const v7 = { "username": v0, "xp": v2, "tags": v4 };
return v7;
```

No payloads, no dispatch, no path arrays. Leaf schemas are inlined into their parent, so a `z.string()` inside an object costs one `typeof`. (The `c0` call is the code-point counter for `.min(2)`; it only runs when the string is short enough that surrogate pairs could change the answer.)

## Why this was hard

The obvious way to build a compiler is to generate everything: one code path that validates, and one that produces the errors when validation fails. ArkType takes this route.

For Zod that would mean a second implementation of every schema type and every check, agreeing with the first on every edge case: dozens of schema types, dozens of checks, 60 locales, and years of error shapes that people snapshot in their test suites. A second implementation of all that was never going to stay in sync.

So Zod's compiler doesn't produce errors at all. Look at the generated code again: every failure is `return INVALID`. The compiled function is a happy-path validator, and when it returns `INVALID`, the wrapper hands the input to the standard parser, which produces the `ZodError` the same way it always has.

```ts
const result = CompiledPlayer.safeParse({ username: "b", xp: 1.5, tags: ["a"] });
result.error.issues;
// [
//   {
//     origin: "string",
//     code: "too_small",
//     minimum: 2,
//     inclusive: true,
//     path: ["username"],
//     message: "Too small: expected string to have >=2 characters"
//   },
//   {
//     expected: "int",
//     format: "safeint",
//     code: "invalid_type",
//     path: ["xp"],
//     message: "Invalid input: expected int, received number"
//   }
// ]
```

That is the error the uncompiled `Player` produces, because the fallback ran the uncompiled `Player` to build it. There is no second error path to drift out of sync, and every fix to the standard parser's error reporting applies to compiled schemas automatically.

Two consequences follow:

- Invalid inputs pay for both the fast path and the fallback. If your workload is mostly invalid input, compilation won't help.
- Refinements and transforms run exactly once on valid input, and at most twice on invalid input: once in the fast path, once in the fallback.

Output parity is tested rather than assumed. The repo runs its entire test suite a second time with compilation enabled globally, asserting per fixture that the fast path actually produced the value rather than silently falling back. Key order, `undefined`-valued versus absent keys, array holes, frozenness, `NaN` and `-0` all match.

## Compiling everything

You don't have to call `z.compile()` on each schema. Import `zod/compile` once, before anything that defines schemas, and every schema constructed after that is compiled on its first parse:

```ts
import "zod/compile"; // must come before modules that define schemas
import * as z from "zod";

const schema = z.object({ name: z.string() });
schema.parse({ name: "ok" }); // compiled on first parse
```

Compilation is lazy, so the intermediate schemas inside a builder chain like `z.string().min(1).max(10).optional()` cost nothing. Only the schemas you actually parse with get compiled.

Global mode is meant for applications, not libraries. A library that imports `zod/compile` opts in every schema in the process on behalf of its users, which is not its decision to make.

## Numbers

Across a 55-schema benchmark in the repo, the median speedup is **2.4x**. It scales with how much work the schema does per parse, because what compilation removes is per-node overhead rather than the checks themselves:

| schema | speedup |
| ------ | ------- |
| `z.array(z.string())`, 100 items | ~14x |
| `z.array(z.object({…}))`, 50 items | ~9x |
| 20-key object | ~9x |
| `.pipe()` chain | ~7.7x |
| tuple | ~4.8x |
| nested object | ~4.5x |
| discriminated union | ~4.3x |
| intersection | ~4.3x |
| strict object | ~3x |
| `z.string().min(3).max(64).regex(…)` | ~2.8x |
| 5-key object | ~2.5x |
| bare `z.string()` | none |

A bare `z.string()` has nothing to remove: the whole schema is one `typeof`. Everything built out of such schemas benefits, because the leaves get inlined into the parent's generated code.

Four corrections to the harness were needed before these numbers meant anything, and they are written up in the repo:

- Results must escape. V8 deletes a parse whose result is discarded; `z.string()` measured 625M ops/sec before this was fixed.
- Inputs must arrive through an array load, not a constant, or the call becomes loop-invariant.
- The number of schemas sharing the process is the single largest lever on the result.
- Compiled and uncompiled runs must be interleaved, because absolute throughput drifts by tens of percent between runs.

## What doesn't compile

The compiler refuses anything it can't model *exactly*. `z.compile()` throws in these cases; global mode silently keeps using the standard parser.

- **Async.** A schema with an async refinement, transform, or check throws `ZodCompileAsyncError`. `safeParseAsync()` always uses the standard parser.
- **Exclusive unions (`z.xor()`).** The exactly-one-match rule needs every branch to reject for the same reason the standard parser would, and a compiled branch that returns `INVALID` can't say why.
- **Recursive schemas.** Cycle detection in the input needs the standard parser's memoizer.
- **Coercion**, checks with a custom `when`, and `.catch()` given a callback rather than a value.

Inside a container — object, array, tuple, record, intersection — an unsupported *child* doesn't prevent compilation. The child runs on the standard parser as an island and the surrounding structure stays compiled. Unions are the exception: a falsely-rejecting compiled branch would corrupt match semantics, so a union with an unsupported member falls back as a whole.

Encoding (`z.encode()` and the codec `"backward"` direction) always uses the standard parser. Backward codegen may come later.

Methods that derive a new schema return uncompiled schemas. Compile the final schema, not an intermediate.

```ts
// ❌ the .refine() result is not compiled
const schema = z.compile(z.string()).refine((val) => val.length > 1);

// ✅ compile last
const schema2 = z.compile(z.string().refine((val) => val.length > 1));
```

## Content Security Policy

Compilation uses `new Function`, which is unavailable under a CSP that forbids `eval`. Global mode stands down automatically when `jitless` is set, so `import "zod/compile"` is inert in those environments:

```ts
z.config({ jitless: true });
```

Calling `z.compile()` directly is treated as an explicit opt-in and throws `ZodCompileUnsupportedError` if code generation is unavailable.

## Cost

A compiler is a lot of code, so the question is what it costs a bundle that never uses it. The compiler itself tree-shakes cleanly: unless you call `z.compile()` or import `zod/compile`, none of it ends up in your bundle.

What every bundle does carry is the hook that global mode needs in the schema constructor. It measured at +21 to +25 bytes gzipped on the smallest `zod/mini` fixtures and below the noise floor on construction speed, and the bundle-size test in CI now holds those fixtures to a ceiling.

## Try it

```sh
npm install zod@^4.5.0
```

Then `z.compile()` the schema on your hottest path, or `import "zod/compile"` at the top of your entry point, and run your test suite.
