Zod 4.6 is now available.

```sh
npm install zod@latest
```

At a glance:

- [`z.instanceof().properties()`](#zproperties) — validates properties of an instance
- [`.validate()`](#validate) — checks input validity without building a result (up to 35x faster than `.safeParse().success` on a compiled schema)
- [`fromJSONSchema()`](#fromjsonschema) — enforces six validation keywords it used to ignore

## `z.properties()`

A new API for validating specific properties of an object. Unlike `z.object()` it validates *in-place*, so it plays nice with class instances. ([#6536](https://github.com/colinhacks/zod/pull/6536))

```ts
const responseLike = z.properties({ status: z.number().min(200).max(299) });

responseLike.parse(new Response("ok"));  // ✅ a real Response
responseLike.parse({ status: 204 });     // ✅ a plain object
```

A `.properties()` method on `z.instanceof()` narrows both at once: the class *and* the properties.

<Tabs groupId="lib" items={["Zod", "Zod Mini"]}>

```ts
const okResponse = z.instanceof(Response).properties({
  ok: z.literal(true),
  status: z.number().min(200).max(299),

```
</Tab>
<Tab value="Zod Mini">
```ts
const okResponse = z.instanceof(Response).check(
  ...z.properties({
    ok: z.literal(true),
    status: z.number().check(z.minimum(200), z.maximum(299)),
  })
);
```
</Tab>
</Tabs>

The input comes back untouched, so the prototype survives and the methods still work. That is the part `z.object()` cannot do: it would hand back a plain object and the `Response` would be gone.

```ts
const res = okResponse.parse(await fetch("/api/user"));

await res.json();  // ✅ still a Response
```


## `.validate()`

Zod 4.5 added `z.validate()`, a boolean check that narrows to the schema's input type. It is a method on Zod Classic schemas now. ([#6547](https://github.com/colinhacks/zod/pull/6547))

```ts
if (Player.validate(data)) {
  data.username; // narrowed
}
```

On a [compiled schema](/compile) it answers straight from the compiled fast path, up to 35.6x faster than `.safeParse().success` on invalid input.

Both charts measure the failure path, where the gap is widest. Valid input is closer: 1.0x to 1.3x on a plain schema, and 1.1x to 2.1x on a compiled one, since a compiled `.validate()` answers without building the output.

Async refinements are covered by `.validateAsync()`, and Zod Mini keeps the top-level function form.

## `fromJSONSchema()`


Six validation keywords were listed as recognized and then silently ignored, so a converted schema accepted data the source schema rejects. All six are enforced now, and all six round-trip back out through `z.toJSONSchema()`. ([#6535](https://github.com/colinhacks/zod/pull/6535))

- [`minProperties`](https://json-schema.org/understanding-json-schema/reference/object#size) / [`maxProperties`](https://json-schema.org/understanding-json-schema/reference/object#size)
- [`uniqueItems`](https://json-schema.org/understanding-json-schema/reference/array#uniqueItems)
- [`contains`](https://json-schema.org/understanding-json-schema/reference/array#contains)
- [`minContains`](https://json-schema.org/understanding-json-schema/reference/array#mincontains-maxcontains) / [`maxContains`](https://json-schema.org/understanding-json-schema/reference/array#mincontains-maxcontains)

```ts
const schema = z.fromJSONSchema({
  type: "object",
  minProperties: 2,      // also maxProperties
});

schema.parse({ a: 1 });        // ❌ too few properties
schema.parse({ a: 1, b: 2 });  // ✅
```

The property counts read the raw input's own keys. On arrays, uniqueness compares structurally, so `[{ a: 1 }, { a: 1 }]` is a duplicate.

```ts
z.fromJSONSchema({ type: "array", uniqueItems: true }).parse([{ a: 1 }, { a: 1 }]); // ❌

z.fromJSONSchema({
  type: "array",
  contains: { type: "number" },   // also minContains and maxContains
  minContains: 2,
}).parse(["a", 2]);               // ❌ only one number
```

## Bug fixes

### ⚠️ Error maps run on the first read of `error`

Because `safeParse()` now builds its error lazily, a global error map, a locale, and a per-schema `error` function all run when `result.error` is first read rather than when the parse happens. Code that swaps `z.config()` between the parse and the read gets the newer configuration. ([#6519](https://github.com/colinhacks/zod/pull/6519))

```ts
const result = schema.safeParse(12);
z.config(z.locales.fr());
result.error.issues[0].message; // French in 4.6, English in 4.5
```

An error map with a side effect never runs at all if nothing reads the error. Throwing parses are unaffected: `.parse()` builds and throws its error on the spot and never takes the lazy path, so its stack still points at your call site.

### ⚠️ `z.emoji()` rejects component-only strings

The emoji class covers the pieces that combine with an emoji, not emoji themselves, so `z.emoji()` accepted `"123"`, `"#"`, `"*"`, and a lone zero-width joiner, variation selector, or skin tone modifier. A leading lookahead now requires at least one real anchor. ([#6532](https://github.com/colinhacks/zod/pull/6532))

```ts
z.emoji().parse("😀");   // ✅
z.emoji().parse("1️⃣");   // ✅ the keycap is the anchor
z.emoji().parse("123");  // ❌ was accepted in 4.5
```

Flags, subdivision flags, skin-tone-modified emoji, and ZWJ sequences are unchanged. Closes [#6515](https://github.com/colinhacks/zod/issues/6515).

### ⚠️ A numeric enum's reverse mappings are out of `.options`

A TypeScript enum carries both directions of its mapping at runtime. The parser already dropped the reverse half, but `.options` was read straight off the entries object, so a three-member numeric enum listed six values — three of which the schema rejects. ([#6542](https://github.com/colinhacks/zod/pull/6542))

```ts
enum Country { UK, Germany, France }

z.enum(Country).options; // 4.5: ["UK", "Germany", "France", 0, 1, 2] — 4.6: [0, 1, 2]
```

### ⚠️ base64 patterns

The runtime patterns for `z.base64()` and `z.base64url()` are the character sets, with length and padding enforced in code, so a multi-megabyte string can no longer overflow the regex stack through a composed schema. The JSON Schema output still emits the exact block forms, so `z.toJSONSchema()` is unchanged. ([#6534](https://github.com/colinhacks/zod/pull/6534), [#6527](https://github.com/colinhacks/zod/pull/6527))

Two consequences. Composing `z.base64()` into a template literal now checks the alphabet but not the length, matching how `z.creditCard()` already behaves there. And `z.regexes.base64url`, which is exported, is now the length-aware form and will overflow on a multi-megabyte input, exactly as `z.regexes.base64` always has.
